Part 01. Data Engineering & Infrastructure

모던 데이터 아키텍처 & 인프라 엔지니어링

초당 수십만 건의 실시간 틱(Event Stream) 처리부터 페타바이트급 분석 질의까지—
전통적 RDB/DW의 병목을 극복하고, 클라우드 오브젝트 스토리지 위에서 ACID 트랜잭션과 실시간성을 동시에 달성하는 현대 데이터 레이크하우스(Lakehouse)와 카파(Kappa) 스트리밍 아키텍처를 심층 분석합니다.

01

엔터프라이즈 데이터 저장소의 4세대 진화

RDBMS ➔ DW ➔ Data Lake ➔ Data Lakehouse

데이터의 폭발적 증가와 AI 워크로드의 등장은 인프라의 저장 및 연산 구조를 근본적으로 바꿨습니다. 컴퓨팅과 스토리지를 분리하고, 비정형 데이터와 정형 데이터의 분석 장벽을 허무는 것이 현대 아키텍처의 핵심입니다.

1세대 (1980s~90s)
전통적 RDBMS
운영계 트랜잭션(OLTP) 전용. 완벽한 ACID를 보장하지만 대용량 분석 질의 시 CPU 락(Lock) 및 수평 확장(Scale-out) 한계.
2세대 (2000s)
데이터웨어하우스 (DW)
전사 통합 분석(OLAP). 정규화/스타 스키마 기반 고성능 SQL 지원, 그러나 독점 하드웨어 고비용 및 비정형 데이터 수용 불가.
3세대 (2010s)
데이터 레이크 (Data Lake)
HDFS / S3에 모든 원천 데이터 무제한 저장. 비용은 혁신적으로 낮췄으나, 트랜잭션 미지원 및 데이터 정합성 부재로 '데이터 늪(Swamp)' 전락.
4세대 (현재 표준)
데이터 레이크하우스 (Lakehouse)
저렴한 오브젝트 스토리지(S3) 위에 메타데이터 레이어(Iceberg, Delta Lake)를 얹어 저비용 + ACID 트랜잭션 + 고속 SQL 동시 실현.
DW vs Data Lake vs Data Lakehouse 아키텍처 심층 비교
비교 항목데이터웨어하우스 (DW)데이터 레이크 (Data Lake)모던 레이크하우스 (Lakehouse)
데이터 포맷독점 정형 테이블 (Proprietary)모든 원천 파일 (CSV, JSON, 이미지 등)오픈 포맷 (Parquet, Iceberg)
ACID 트랜잭션완벽 지원미지원 (Dirty Read, 일관성 파괴)완벽 지원 (스냅샷 격리, 롤백)
타임 트래블 (Time Travel)제한적 (스냅샷 백업)불가능과거 특정 시점 쿼리 기본 지원
ML/AI 직접 연동취약 (SQL 외부 언어 연동 번거로움)직접 파일 I/O로 우수Spark, PyTorch 직통 직접 로드 지원
비용 효율성매우 고비용 (스토리지/컴퓨팅 종속)최저 비용 (단순 파일 저장)최고 가성비 (오브젝트 스토리지 기반)
02

엔터프라이즈 정제 파이프라인: 메달리온 아키텍처

Bronze ➔ Silver ➔ Gold 단계별 데이터 성숙도 모델

데이터 레이크하우스 내부에서 원천 데이터가 프로덕션 비즈니스 분석 및 머신러닝 피처로 정제되는 표준적인 3단계 파이프라인 계층입니다.

BRONZE LAYER
Raw Data (원천 복제본)
• 특성: API, CDC, 웹소켓 등에서 들어온 원본을 단 1바이트의 유실도 없이 있는 그대로 적재 (Append-Only).
• 목적: 언제든 과거 데이터를 원형 복원하고 재처리(Reprocessing)할 수 있는 무결성 원천 보존.
SILVER LAYER
Cleaned & Conformed (정제 엔터프라이즈)
• 특성: 스키마 유효성 검사, 결측치 처리, 데이터 타입 캐스팅, 중복 제거(Deduplication) 및 공통 마스터 조인 수행.
• 목적: 전사 분석가와 데이터 사이언티스트가 신뢰하고 즉시 쿼리할 수 있는 SSOT(단일 진실 공급원).
GOLD LAYER
Business Aggregated (비즈니스 서빙)
• 특성: 비즈니스 규칙(KPI), 일/월 단위 집계, 코호트 매트릭스 및 실시간 ML 모델링용 피처(Feature) 마트로 최종 가공.
• 목적: C-Level 경영진 대시보드(BI) 및 초저지연 머신러닝 추론 서빙(Feature Store).
03

람다(Lambda)의 종말과 카파(Kappa) 실시간 아키텍처

Kafka + Apache Flink 기반의 0ms 레이턴시 이벤트 파이프라인

과거에는 실시간성을 위해 람다 아키텍처(배치 계층 + 스피드 계층)를 도입했으나, 동일한 비즈니스 로직을 두 개의 다른 엔진으로 이중 개발하고 유지보수해야 하는 지옥이 발생했습니다. 현대는 **카파 아키텍처(단일 이벤트 스트림)**로 통합되었습니다.

람다 아키텍처 (과거의 기술 부채) vs 카파 아키텍처 (현대 표준)
람다 아키텍처 (Lambda)
• 구조: 배치 계층(Hadoop/Spark) + 실시간 계층(Storm/Flink) + 서빙 계층.
• 치명적 결함: 코드 베이스 이중화, 실시간 뷰와 배치 뷰 간의 데이터 정합성 불일치 발생, 버그 수정 시 양쪽 파이프라인 동시 패치 필요.
카파 아키텍처 (Kappa)
• 구조: 오직 단일 이벤트 로그 스트림(Kafka)과 단일 스트림 처리 엔진(Flink)만으로 실시간과 과거 재처리(Replay)를 모두 해결.
• 핵심 이점: 단 하나의 비즈니스 코드 베이스, 0ms 레이턴시 실시간 전송과 과거 데이터 전체 리플레이의 완벽한 일관성.
실시간 스트리밍의 4대 프로덕션 엔지니어링 표준
  • 1. 0ms 직통 토스 우선 (Direct Toss First): 데이터 수신 시 무거운 파싱이나 연산보다 대기 중인 컨슈머/웹소켓으로의 전송을 0순위로 즉각 실행.
  • 2. 백프레셔(Backpressure) 방어 의무화: 지연되는 클라이언트의 버퍼가 임계치(예: >1MB)를 초과하면 즉시 연결을 강제 종료하여 서버 OOM 및 GC 프리징 차단.
  • 3. 중복 브로드캐스트 원천 차단: 단일 루프 1회 전송을 보장하여 시스템 내부의 이중 틱 전송 버그를 제거.
  • 4. 압축 오버헤드 배제: 초고주파 스트리밍에서는 CPU 점유와 버퍼 메모리 할당을 줄이기 위해 메시지 단위 압축(zlib 등)을 선별적 비활성화.
04

데이터 정합성 보장: Data Lineage & Data Contracts

상류(Upstream) 변경으로 인한 하류(Downstream) 장애 방어

실무에서 데이터 엔지니어가 가장 고통받는 순간은 프론트엔드/백엔드 개발자가 사전 공지 없이 DB 컬럼명을 바꾸거나 데이터 타입을 수정하여 하류의 모든 ETL과 머신러닝 모델이 다운되는 것입니다.

1. 데이터 계약 (Data Contracts)
API 계약처럼 데이터 생산자(개발팀)와 소비자(데이터팀) 간에 스키마(Schema), SLA, 업데이트 빈도를 명문화하고 CI/CD 테스트 시 위반 여부를 자동 차단.
2. 데이터 리니지 (Data Lineage)
데이터가 어디서 생성되어 어떤 dbt/Spark 모델을 거쳐 어떤 대시보드와 머신러닝 피처로 흘러가는지 전체 계보를 시각적 DAG로 추적하는 투명성 확보.
3. Data Observability 5대 기둥
데이터의 신선도(Freshness), 용량(Volume), 스키마(Schema), 리니지(Lineage), 품질(Quality) 이상 징후를 실시간 감시하는 APM 모니터링 체계.
